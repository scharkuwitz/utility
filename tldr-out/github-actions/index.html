GitHub Actions, from CI/CD basics to PR audits

From docs.github.com/en/actions · condensed 11 November 2026 · 49 min read

These pages condense about 7,000 lines of GitHub’s documentation on GitHub Actions, its CI/CD guides, and its code security features into about 50 minutes of reading. They are written for a developer who knows Git, GitHub pull requests, and Python or TypeScript, but has never set up continuous integration. The first page explains CI/CD itself; the rest build up to automated audits of a codebase and its pull requests.

When you finish, you should be able to write a workflow that lints and tests a Python or TypeScript project on every pull request, add audit jobs that annotate risky lines and block vulnerable dependencies, and avoid the mistakes that let a pull request steal a repository’s secrets.

BackgroundGeneral knowledge, not from the source documentation.

What to know first

You need a GitHub repository you can push to, and a working test command for your project (pytest, npm test). Workflows are written in YAML; Writing workflows has a one-paragraph YAML primer. Every example runs on GitHub-hosted runners; nothing needs a server of your own.

CI/CD from zero

Continuous integration (CI) means that every change pushed to a shared repository is built and tested automatically, so a mistake shows up minutes after it is made, not weeks later. Continuous deployment (CD) extends the same automation past the tests: once a change passes, a machine publishes or deploys it. Together they are written CI/CD. A pipeline is the sequence of automated steps (install, lint, test, build, deploy) that runs on every change. GitHub Actions is one system that runs such pipelines, next to your code on GitHub.

The problem CI solves

Picture a team of five working without CI. Each person works on a branch for two weeks, runs the tests they remember to run, and merges. On merge day, the branches conflict, the tests that nobody ran fail, and nobody knows which of 80 commits broke them. The fix is slow because the cause is buried.

CI shrinks the gap between making a mistake and learning about it. GitHub’s definition puts it this way: committing code often “detects errors sooner and reduces the amount of code a developer needs to debug when finding the source of an error.”[1] If the tests run on every push, a failure points at one small change.

The second idea is that the checks run on a neutral machine. “Building and testing your code requires a server.”[2] A clean server has no leftover files, no globally installed tools you forgot about and no uncommitted changes, so “works on my machine” stops being an answer.

BackgroundGeneral knowledge, not from the source documentation.

Vocabulary used on every page

Repository: the project’s Git history on GitHub. Commit: one saved change. Branch: a line of commits, such as main or fix-login. Push: sending commits to GitHub. Pull request (PR): a request to merge one branch into another, where teammates review the change. Merge: combining the branch into the target.

Linter: a program that checks style and common mistakes without running the code (Ruff for Python, ESLint for TypeScript). Unit test: code that calls your code and checks the result (pytest, Vitest, Jest). Build: turning source into what you ship, such as compiling TypeScript to JavaScript or making a Python wheel. Artifact: a file a pipeline produces and keeps, such as a test report or a built package.

Exit code: the number a program returns when it ends. 0 means success; anything else means failure. CI systems decide pass or fail from exit codes, so a test runner that exits 1 fails the pipeline.

What a pipeline does

The CI part is everything up to and including the checks. GitHub’s CI page lists what those checks commonly include: “code linters (which check style formatting), security checks, code coverage, functional tests, and other custom checks.”[3] The result is reported back where people are already looking: GitHub “provides the results of each test in the pull request, so you can see whether the change in your branch introduces an error.”[4]

The CD part runs after the checks. GitHub defines continuous deployment as “the practice of using automation to publish and deploy software updates”, with the code “automatically built and tested before deployment.”[5] Most teams deploy only from the main branch, after a pull request is merged, while CI runs on every branch and every pull request.

Delivery or deployment

The “D” is used two ways. Continuous delivery means every passing change is ready to release, and a person presses the button. Continuous deployment means the release happens automatically. GitHub Actions supports both: environments can “require approval for a job to proceed”, which turns automatic deployment into delivery with a human gate.[6]

Where GitHub Actions fits

Without a hosted service, you would run your own CI server (Jenkins is a common example) and connect it to GitHub with webhooks. GitHub Actions removes that setup: the pipeline definition is a YAML file in your repository, and GitHub supplies the machines. Workflows “can run on GitHub-hosted virtual machines, or on machines that you host yourself.”[7]

CI and CD are practices, and GitHub Actions is a tool for them. The same YAML file that runs tests can also label issues, post comments on pull requests or audit dependencies, which is why the rest of this bundle treats Actions as a general automation system that happens to be good at CI.

Check yourself

  1. Why does running tests on every push make bugs cheaper to fix?

    The failure points at one small change instead of weeks of commits, so there is little code to search.[1]

  2. Why run the checks on a server instead of trusting a local test run?

    A fresh machine has no leftover state, so it catches missing dependencies and uncommitted files.

  3. What decides whether a pipeline step passed?

    The exit code of the command: 0 passes, anything else fails.

  4. What is the difference between continuous delivery and continuous deployment?

    Delivery keeps every passing change ready and a person releases it; deployment releases automatically.

  5. Where does a developer see CI results on GitHub?

    On the pull request, as checks that pass or fail.[4]

GitHub Actions is GitHub’s built-in automation system. You commit a YAML file under .github/workflows/, and GitHub runs it on its own machines whenever something happens in the repository: a push, a pull request, a new issue, a schedule. GitHub describes it as “a continuous integration and continuous delivery (CI/CD) platform that allows you to automate your build, test, and deployment pipeline.”[4] Use it to test every pull request, deploy merged code, and automate repository chores such as labeling issues or auditing changes.

How it works

Five nouns describe the whole system. GitHub’s own summary: a workflow is triggered when an event occurs; it “contains one or more jobs which can run in sequential order or in parallel”; each job runs on its own runner and “has one or more steps that either run a script that you define or run an action.”[5]

Event

Something that happened, such as push, pull_request or schedule. “An event is a specific activity in a repository that triggers a workflow run.”[6]

Workflow

One YAML file. A repository can have many, each with its own triggers. Workflows “will run when triggered by an event in your repository, or they can be triggered manually, or at a defined schedule.”[7]

Job

A group of steps that share one machine. By default “jobs have no dependencies and run in parallel”; needs: makes one job wait for another.[8]

Step

One command (run:) or one action (uses:). Steps in a job run in order, and since they share the runner, “you can share data from one step to another.”[9]

Action

A packaged, reusable step written by GitHub or anyone else, referenced as owner/repo@version. Typical uses: check out the code, install a language, log in to a cloud.[10]

Runner

The machine. “Each runner can run a single job at a time” and “each workflow run executes in a fresh, newly-provisioned virtual machine.”[11]

The consequences that matter

The model predicts most of what surprises newcomers:

  1. A runner starts empty. It does not have your code until a step checks it out. That is why almost every job starts with actions/checkout.
  2. Jobs don’t share files. Two jobs are two machines. To pass a build from build to deploy, upload it as an artifact or recompute it. Steps within one job share files freely.
  3. Steps don’t share environment variables. Each step “runs in its own process”, so “changes to environment variables are not preserved between steps.”[12] Use the GITHUB_ENV and GITHUB_OUTPUT files instead (Writing workflows).
  4. A failing step fails the job, and a failing job fails the run. A job that needs: a failed job is skipped.[13]
  5. The workflow file is code in the repository. It is reviewed in pull requests, versioned with the code, and can be changed by anyone who can push. This matters for security (Workflow security).

Check yourself

  1. Two jobs in the same workflow both need the source code. How many checkout steps do you need, and why?

    Two. Each job runs on its own fresh runner, which starts empty.[11]

  2. Jobs lint and test have no needs:. In what order do they run?

    In parallel; jobs have no dependencies by default.[8]

  3. A step runs export TOKEN=abc. Why is $TOKEN empty in the next step?

    Each step runs in its own process, so environment changes don’t carry over.[12]

  4. What is the difference between run: and uses:?

    run: executes a shell command; uses: runs a packaged action.

  5. When does ${{ github.ref }} get its value?

    GitHub evaluates the expression before the step’s shell runs, and substitutes the text.

A workflow file is a YAML document with three top-level parts: on (when to run), jobs (what to run) and optional settings that apply to every job, such as permissions, env and concurrency. This page covers the keys found in nearly every CI file, and the rules that cause most surprises: how filters combine, when jobs are skipped, and how data moves between steps and jobs.

BackgroundGeneral knowledge, not from the source documentation.

YAML in one paragraph

YAML expresses nested data with indentation (spaces only, never tabs). key: value is a mapping entry; a line starting with - is a list item. [a, b] is an inline list. | starts a multi-line string, used for multi-line shell scripts. Strings rarely need quotes, but quote values that look like numbers ("3.10", otherwise read as 3.1) or start with special characters such as *, ! or {.

A complete CI file

Start with a realistic file. Every key in it is explained below.

Triggers: on

on lists the events. Each event can take filters.

EventFires whenCommon filters
pushCommits are pushedbranches, tags, paths
pull_requestA PR is opened, updated or reopenedbranches (the target), paths, types
scheduleA cron time is reachedcron
workflow_dispatchSomeone presses Run workflowinputs
pull_request_targetSame as pull_request, but runs with the base repository’s privilegessee Workflow security

Defaults that matter:

  • pull_request with no types runs only for opened, synchronize or reopened.[1] synchronize means new commits were pushed to the PR branch.
  • A pull_request run tests the merge of your branch into the target, not your branch alone: “Your CI tests run against the merged result, not just the head branch alone.”[2]
  • schedule uses cron syntax in UTC, runs “on the latest commit on the default branch”, and can’t run more often than every 5 minutes.[3] In public repositories, scheduled workflows “are automatically disabled when no repository activity has occurred in 60 days.”[4]
  • workflow_dispatch “only receives events when the workflow file is on the default branch.”[5] A manual button added on a feature branch does not appear until merged.

Filters combine with AND

branches and paths on the same event must both match: “If you define both branches/branches-ignore and paths/paths-ignore, the workflow will only run when both filters are satisfied.”[6] You can’t use paths and paths-ignore on the same event; to exclude inside an include list, prefix a pattern with !, and order matters.[7]

WarningPath filters and required checks

If a workflow is skipped by a paths or branches filter, its checks stay Pending and a pull request that requires them is blocked from merging.[8] Keep required checks unfiltered, or decide inside the job with if:.

Jobs: order, conditions, matrices

needs

Jobs start in parallel. needs: [a, b] makes a job wait for both. If a needed job fails or is skipped, every job downstream is skipped too, “unless the jobs use a conditional expression that causes the job to continue”, such as if: ${{ always() }}.[9]

if

if: on a job or step skips it unless the expression is true. You can leave out ${{ }} in if, except when the expression starts with !, because “! is reserved notation in YAML format.”[10]

strategy.matrix

A matrix turns one job definition into one job per combination of values. Each combination’s values are in the matrix context. With two lists of 3 and 2 values, you get 6 jobs; the cap is 256 per run.[11] exclude drops combinations. fail-fast defaults to true, so “GitHub will cancel all in-progress and queued jobs in the matrix if any job in the matrix fails.”[12] Set fail-fast: false when you want to see every version’s result.

WarningExpressions are pasted into the script

${{ }} substitutes text before the shell runs. If the value comes from a user (a PR title, a branch name, a comment), they can inject shell commands. Pass such values through env: and use "$VAR" in the script. See Script injection.

Passing data

Steps in one job share the file system but not environment variables. Jobs share neither. Use these files and keys:

To passFromToUse

With GITHUB_ENV, “the step that creates or updates the environment variable does not have access to the new value, but all subsequent steps in a job will have access.”[13] A step output needs an id on the step that writes it.[14]

Permissions and secrets

Every job gets an automatic token, GITHUB_TOKEN, scoped to the repository. permissions: sets what it may do. If you list any permission, “all of those that are not specified are set to none.”[16] Set read-only at the top and raise it per job:

Secrets you add in the repository settings appear as ${{ secrets.NAME }}. They are not available to workflows triggered from forks: “With the exception of GITHUB_TOKEN, secrets are not passed to the runner when a workflow is triggered from a forked repository.”[17]

Concurrency

concurrency.group names a lane; at most one run per lane. A new run waits as pending, and with cancel-in-progress: true it cancels the running one instead.[18] Group by github.ref for CI (only the latest push per branch matters). For deployments, use a fixed group such as deploy-production without cancel-in-progress, so a deployment is never cut off halfway.

Check yourself

  1. A workflow has on: push: branches: [main] and paths: ['src/**']. Does a push to main that only changes README.md run it?

    No. Branch and path filters must both match.[6]

  2. Which three pull_request activity types run a workflow by default?

    opened, synchronize and reopened.[1]

  3. What code does a pull_request run test, by default?

    The merge of the PR branch into the target branch.[2]

  4. A matrix has os: [ubuntu, windows] and python: [3.11, 3.12, 3.13]. How many jobs run, and what happens when one fails?

    Six. With the default fail-fast: true, the rest are cancelled.[12]

  5. A workflow sets permissions: pull-requests: write. Can it still read the repository contents?

    No. Listing any permission sets the unlisted ones to none; add contents: read.[16]

  6. Step A writes VERSION=1.2 to $GITHUB_ENV. Which steps can read $VERSION?

    Only later steps in the same job; not step A itself, and not other jobs.[13]

  7. Why can’t a PR from a fork use your PYPI_TOKEN secret?

    Secrets other than GITHUB_TOKEN are not passed to runs triggered from forks.[17]

A CI workflow for a Python or TypeScript project has the same four steps: check out the code, install the language at a pinned version with actions/setup-python or actions/setup-node, install dependencies from the lock file with caching, and run the same commands you run locally: lint, type-check, test. GitHub’s tutorials put the last point plainly: “You can use the same commands that you use locally to build and test your code.”[1] This page gives a complete file for each language, then the variations people need most.

Why the setup actions

Runners come with some Python and Node.js preinstalled, but which version you get “varies between GitHub-hosted runners, which may cause unexpected changes or use an older version than expected.”[2] The setup actions pin the version: setup-python “finds a specific version of Python or PyPy from the tools cache on each runner and adds the necessary binaries to PATH”, downloading it if missing.[3] setup-node does the same for Node.js.[4]

Both also cache the package manager’s download cache when you pass cache:. setup-python looks for the dependency file (requirements.txt, Pipfile.lock or poetry.lock) “in the whole repository” to build the cache key.[5] A changed lock file means a new cache.

An audit job is an ordinary workflow job that runs on pull_request, inspects the change, and reports what it found. The report can be a failed check, which can block merging, annotations pinned to lines in the diff, a Markdown job summary, a comment on the pull request, or code scanning alerts in the repository’s Security tab. GitHub supplies two scanners, code scanning (CodeQL) and dependency review. Any linter or script that prints in the right format can join them. Use audit jobs for rules your team keeps repeating in review: no debugger calls, no unreviewed dependencies, no secrets, no dangerous workflow changes.

How it works

Every audit, built-in or homemade, has the same shape: read the change, apply rules, report through one or more channels. What differs is where the report lands and who can see it.

The reporting channels

ChannelHow a job produces itWhere it showsWorks on fork PRs

Annotations are the most useful channel for a homemade audit. An error command “will create an annotation, which can associate the message with a particular file in your repository” and can point at a line.[2] The format is one line on standard output:

::warning and ::notice use the same parameters. Anything a step prints in this form becomes an annotation, so a script in any language can produce them, and so can linters that support it (Ruff’s --output-format=github).

Job summaries are for the overview: counts, tables, links. Summaries are meant to show results “so that someone viewing the result of a workflow run doesn’t need to go into the logs”.[3]

Merge gates. A check only blocks merging when the branch is protected with required status checks. GitHub’s dependency review docs describe the pattern: “A failed check blocks a pull request from being merged when the repository owner requires the dependency review check to pass.”[4] The same setting works for any job name.

Checkout depth

actions/checkout fetches only the latest commit by default; fetch-depth: 0 fetches all history. This comes from the actions/checkout README, not from the pages condensed here. On a pull_request run, HEAD is the temporary merge commit, so base...HEAD is exactly what the PR adds.

Built-in scanners

Code scanning with CodeQL

Code scanning is GitHub’s static analysis, “a feature that you use to analyze the code in a GitHub repository to find security vulnerabilities and coding errors”. It shows alerts in the repository, and closes an alert when the code that triggered it is fixed.[8] It runs on Actions and uses Actions minutes. On private repositories it needs a GitHub Code Security license.[9]

Two ways to turn it on:

  • Default setup: enable it in the repository’s security settings. No workflow file to write. Start here.
  • Advanced setup: a CodeQL workflow file you control, from GitHub’s code scanning templates.[10]

CodeQL can also scan your workflow files themselves: it “can scan and detect potentially vulnerable GitHub Actions workflows” when Actions scanning is enabled in default setup.[11] That covers the injection and pull_request_target mistakes on Workflow security.

Third-party tools through SARIF

Any analyzer that writes SARIF can feed the same alert system: code scanning “is interoperable with third-party code scanning tools that output Static Analysis Results Interchange Format (SARIF) data.”[12] Many security tools can write SARIF. Upload the file, and its findings appear as alerts next to CodeQL’s.

A workflow runs code with credentials: the automatic GITHUB_TOKEN, plus any secrets you add. Anything that can change what that code does can use those credentials. The main risks come from four mistakes: tokens with more permission than needed, untrusted text pasted into shell scripts (script injection), running a pull request’s code under the privileged pull_request_target trigger, and third-party actions referenced by a tag that someone can move. Read this page before writing any workflow that handles pull requests from people outside your team, which includes every audit workflow on a public repository.

How it works

Security in Actions comes down to one question per workflow: whose code runs, and with which credentials?

The pull_request trigger handles forks safely by default. For fork PRs, “the GITHUB_TOKEN has read-only permissions”[1] and other secrets “are not passed to the runner”.[2] The fork’s code runs, but it has nothing worth stealing.

The pull_request_target trigger is the opposite trade. It “runs in the context of the default branch of the base repository”, so the workflow file comes from your trusted branch, and it can “label or comment on pull requests from forks.”[3] It also gets a read/write token, “even when it is triggered from a public fork.”[4] That is safe only as long as the workflow never runs the PR’s code.

GitHub’s warning is direct: these triggers, “when used with the checkout of an untrusted pull request, expose the repository to security compromises” and “can be exploited to take over a repository.”[5]

Least privilege for the token

Every job gets a GITHUB_TOKEN, and actions can read it from the github.token context “even if the workflow does not explicitly pass the GITHUB_TOKEN to the action.”[6] So every third-party action in a job holds whatever that job’s token can do. GitHub recommends setting the default “to read access only for repository contents” and raising it per job.[7]

Listing any permission sets every unlisted one to none.[8] The token expires when the job finishes, or after 24 hours at most.[9]

Script injection

${{ }} expressions are replaced with text before the shell runs. If that text comes from an attacker, it becomes part of your script.

The same applies to Python and TypeScript scripts in run:: read untrusted values from os.environ or process.env, never from text spliced into the command line. Passing the value as an input to an action (with:) is also safe, because it is “passed to the action as an argument” rather than used to generate a shell script.[12]

Secrets

  • Anyone with write access can read every secret. “Any user with write access to your repository has read access to all secrets configured in your repository.”[13] Keep secrets narrow in scope.
  • Redaction is best effort. Logs hide exact secret values, so “automatic redaction is not guaranteed” once a value is transformed.[14] Don’t store JSON or YAML blobs as one secret: structured data “can cause secret redaction within logs to fail”.[15] Register derived values (a JWT, a Base64 form) as secrets too, or mask them with ::add-mask::.[16]
  • If a secret reaches a log, rotate it. Delete the log and rotate the secret.[17]
  • Gate deployment secrets. Environment secrets with required reviewers are unavailable “until approval is granted by a reviewer.”[18]

Third-party actions

A compromised action “would have access to all secrets configured on your repository, and may be able to use the GITHUB_TOKEN to write to the repository.”[19] A tag such as @v3 can be moved to new code by whoever controls the action’s repository. In order of strength:
