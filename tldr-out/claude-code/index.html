Claude Code Docs: Summaries

Source: https://code.claude.com/docs · 8 pages · 35 min read

Three topics: skills; running agents in parallel (with subagents, worktrees and workflows); and plugins (with installing and creating). Overview pages come first in each group.

Contents

01Claude Code Skills
A skill is a folder containing SKILL.md. Its description decides when Claude loads it; its location decides who gets it.
02Running Agents in Parallel
Claude Code offers five ways to run several tasks at once. Choose by who coordinates the work, whether workers communicate, and whether they edit the same files.
03Claude Code Subagents
A subagent is a Markdown file that defines a worker with its own context, tools and permissions. Claude delegates to it by description and receives a summary.
04Worktrees
A git worktree gives each Claude Code session its own files and branch on shared history, so parallel sessions and subagents do not overwrite each other.
05Dynamic Workflows
A dynamic workflow is a script Claude writes to run many subagents in the background. The script, not Claude, holds the plan and the intermediate results.
06Claude Code Plugins
A plugin packages skills, agents, hooks and MCP servers as one installable unit, usually distributed through a marketplace.
07Installing and Managing Plugins
Install plugins by name from a known marketplace, choose a scope, and manage them in /plugin or from the shell.
08Creating a Plugin
A plugin is a directory with a manifest at .claude-plugin/plugin.json and components at the plugin root. Load it with --plugin-dir while developing.

Claude Code Skills

Source: https://code.claude.com/docs/en/skills · Retrieved 2026-11-11 · 5 min read

A skill is a folder containing SKILL.md. Its description decides when Claude loads it; its location decides who gets it.

SectionsKey conceptsExercisesCommon pitfallsLower priorityQuick referenceReview questionsSources

Key concepts Retain these.

01A skill is a folder with a SKILL.md file

SKILL.md holds YAML frontmatter (when to use the skill) and markdown instructions (what to do). The directory name, or frontmatter name, becomes the /command. Detailed material goes in supporting files that SKILL.md links to, so it loads only when needed.1,2
WhyA short SKILL.md keeps context cost low; reference files and scripts carry the detail.
  1. “Every skill needs a SKILL.md file with two parts” — Skills > Create your first skill
  2. “Keep SKILL.md under 500 lines. Move detailed reference material to separate files.” — Skills > Add supporting files

02The description is the trigger

Claude reads the description of each skill and uses it to decide whether to load the full skill. Put the key use case first and include words users would naturally say.1,2
WhyA vague description means the skill is not used automatically. Malformed YAML leaves the skill callable by /name but not matchable.
  1. “Claude uses this to decide when to apply the skill.” — Skills > Frontmatter reference
  2. “Check the description includes keywords users would naturally say” — Skills > Troubleshooting

03Location decides who gets the skill

Personal skills (~/.claude/skills/) apply to all your projects; project skills (.claude/skills/) apply to one repository and can be committed. Enterprise, nested, plugin and claude.ai account locations also exist. On a name clash, enterprise beats personal, and personal beats project.1,2
WhyCommit project skills to share them with the team; keep personal workflows in your home directory.
  1. “Where you save a skill decides which sessions load it.” — Skills > Choose where skills load
  2. “Enterprise over personal, and personal over project.” — Skills > Resolve skills that share a name

04You can control who invokes a skill

disable-model-invocation: true makes a skill manual only; use it for side effects such as deploy or commit. user-invocable: false makes it background knowledge that only Claude can invoke.1,2
WhyOtherwise Claude may start a workflow with side effects when it judges the moment suitable.
  1. “Claude can't invoke the skill on its own.” — Skills > Control who invokes a skill
  2. “Only Claude can invoke the skill.” — Skills > Control who invokes a skill

05Invoked skill content stays in context

Once invoked, the rendered content stays in the conversation as one message and is not re-read from disk. After compaction, only the first 5,000 tokens of each skill are kept.1,2,3
WhyEvery line has a recurring token cost. Write guidance that applies to the whole task and put the most important instructions first.
  1. “stays there across later turns” — Skills > Skill content lifecycle
  2. “keeping the first 5,000 tokens of each” — Skills > Skill content lifecycle
  3. “every line is a recurring token cost” — Skills > Types of skill content

06Dynamic context and forked subagents

A line such as !git diff HEAD` is replaced with the command output before Claude reads the skill. context: fork` runs the skill in a separate subagent that has no access to the conversation history.1,2
WhyInjected commands give Claude live data instead of guesses. Forked skills must be self-contained.
  1. “Claude Code runs the command and replaces the line with its output before Claude sees the skill content” — Skills > Create your first skill
  2. “The subagent doesn't see your conversation history, so the skill's instructions have to stand on their own.” — Skills > Run skills in a subagent

Exercises Hands-on practice.

01Create a skill that injects live context

Observe automatic loading and dynamic context injection in one skill.
  1. Run mkdir -p ~/.claude/skills/summarize-changes
  2. Save the content below as ~/.claude/skills/summarize-changes/SKILL.md
  3. In a git repository with uncommitted changes, ask Claude what changed. Then run /summarize-changes directly.
---
description: Summarizes uncommitted changes and flags anything risky. Use when the user asks what changed, wants a commit message, or asks to review their diff.
---

## Current changes

!`git diff HEAD`

## Instructions

Summarize the changes above in two or three bullet points, then list any risks you notice.
VerifyClaude summarizes your actual diff without you pasting it, in both cases.
VariationReplace the description with a vague one, such as 'helps with code', and test whether it still loads automatically.

02Make a skill manual only

Observe the effect of disable-model-invocation.
  1. Create .claude/skills/deploy/SKILL.md with a short description and disable-model-invocation: true
  2. Ask Claude in plain language to deploy
  3. Run /deploy staging
VerifyClaude does not run the skill on its own, but runs it when you type the command.
VariationChange the field to user-invocable: false and confirm the /deploy command is no longer available to you.

03Move detail into a supporting file

Practise keeping SKILL.md short.
  1. Add reference.md to the skill folder from exercise 1 with a list of risk categories
  2. In SKILL.md, add a line: For risk categories, see [reference.md](reference.md)
  3. Invoke the skill again
VerifyClaude's risk list reflects the categories in reference.md.
VariationRemove the link from SKILL.md and compare the result.

Common pitfalls

  • Frontmatter only counts when the opening --- is the first line of the file. Otherwise the markers become skill content.
  • Unrecognized frontmatter field names are ignored without an error. Match the field names exactly, hyphens included.
  • After compaction, only the start of a skill is kept. Re-invoke the skill, or move rules that must always hold into a hook.
  • An allowed-tools grant clears when you send your next message, although the skill content remains.

Lower priority Valid but rarely needed. Consult when required.

Nested and monorepo discoverySkills in <subdir>/.claude/skills/ load for sessions in or below that directory.
Skills from --add-dirAdditional directories. Same-named skills run under a prefixed name.
Skills synced from claude.aiAccount-level skills. The folder names synced and anthropic-skills are reserved.
Legacy command files.claude/commands/*.md still works. Prefer skills for new work.
Pre-approved tools and argumentsallowed-tools frontmatter and $ARGUMENTS substitution.
Restricting and overriding visibilityPermission deny rules and skillOverrides in settings.

.claude/skills/<name>/SKILL.mdProject skill. Commit it to share with the team.

Review questions Answer first, then expand.

What does Claude use to decide whether to load a skill automatically?

The description frontmatter, plus when_to_use if set.

The same skill name exists in personal and project locations. Which runs?

The personal one.

How do you prevent Claude from running a deploy skill by itself?

Set disable-model-invocation: true.

Where should large reference material go?

In supporting files linked from SKILL.md, which should stay under 500 lines.

Why might Claude stop following a skill late in a session?

The content is not re-read each turn, and compaction keeps only the start. Re-invoke it or use a hook.

What does a skill with context: fork not see?

The conversation history.

Running Agents in Parallel

Source: https://code.claude.com/docs/en/agents · Retrieved 2026-11-11 · 4 min read

Claude Code offers five ways to run several tasks at once. Choose by who coordinates the work, whether workers communicate, and whether they edit the same files.

SectionsKey conceptsExercisesCommon pitfallsLower priorityQuick referenceReview questionsSources

Key concepts Retain these.

01Five approaches, one kind of worker

Subagents (delegated workers inside one session), agent view (dispatch and monitor background sessions), agent teams (a lead with coordinated teammates), dynamic workflows (a script that runs many subagents) and projects (long-running cloud threads). In every case the workers are Claude sessions.1,2
WhyThey differ in control and location, not in capability. Pick by how involved you want to stay.
  1. “Claude Code has five ways to work on several tasks at once” — Run agents in parallel
  2. “In every approach the workers are Claude sessions.” — Run agents in parallel

02Choose by three questions

Who coordinates: Claude inside one conversation (subagents), you (agent view), a lead Claude (agent teams), or a script (workflows). Do workers need to talk to each other? Do they edit the same files?1
WhyAnswering these three questions removes most of the ambiguity between the approaches.
  1. “The right approach depends on who coordinates the work, whether the workers need to communicate, and whether they edit the same files” — Run agents in parallel > Choose an approach

03Results flow back differently

Subagents report to the conversation that spawned them. Agent view sessions report only to you. Agent team teammates message each other directly. Sessions you run yourself can share findings through cross-session messaging.1
WhyPick an approach that delivers results where you need them.
  1. “Subagents report results back to the conversation that spawned them, and agent view sessions report results only to you.” — Run agents in parallel > Choose an approach

04Isolate file edits with worktrees

When parallel work touches the same files, give each session or subagent its own git worktree. Agent teams do not use worktrees, so split the files between teammates.1
WhyWithout isolation, parallel edits collide.
  1. “Agent teams don't isolate teammates in worktrees” — Run agents in parallel > Choose an approach

05Parallel work multiplies cost

Each running session or subagent consumes tokens. Running many at once raises usage proportionally.1
WhyParallelism trades tokens for wall-clock time.
  1. “Running several sessions or subagents at once multiplies token usage.” — Run agents in parallel

Exercises Hands-on practice.

01Map your next task to an approach

Apply the three questions.
  1. Pick a real task, such as a refactor across 20 files
  2. Answer: who coordinates, do workers communicate, do they share files
  3. Name the approach and whether worktrees are needed
VerifyYou can justify the choice with the three answers.
VariationChange one answer (for example, workers now share files) and see which approach changes.

02Find each status command

Learn where to check on running work.
  1. Start a background subagent in a session
  2. Run /tasks to list it
  3. Run /agents and note that it only points to subagent file locations
VerifyYou can say which command shows background items in the current session.
VariationRun claude agents from your shell and compare.

Common pitfalls

  • /agents (in a session) and claude agents (agent view) are different commands.
  • Agent teams are experimental and disabled by default.
  • /batch is a packaged use of subagents and worktrees, not a separate coordination style.

Lower priority Valid but rarely needed. Consult when required.

Agent viewResearch preview. Opened with claude agents.
Agent teamsExperimental and disabled by default.
ProjectsCloud and desktop threads on claude.ai/code.
Cross-session messagingSessions pass findings to each other.
Forked subagentsInherit the full conversation; start with /subtask. Covered on the subagents page.
Background bash and cloud scheduled tasksRun without you, but do not split work across agents.

Quick reference

claude agentsOpen agent view for background sessions.
/tasksList, attach to or stop background items in this session.
/workflowsList workflow runs and their phases.
/batchSplit one large change into 5 to 30 worktree-isolated subagents.
/subtaskStart a forked subagent.

Review questions Answer first, then expand.

Name the five approaches.

Subagents, agent view, agent teams, dynamic workflows, projects.

What three questions choose between them?

Who coordinates, whether workers communicate, whether they edit the same files.

Where do subagent results go?

Back to the conversation that spawned them.

What do agent teams lack that subagents can have?

Worktree isolation.

Claude Code Subagents

Source: https://code.claude.com/docs/en/sub-agents · Retrieved 2026-11-11 · 5 min read

A subagent is a Markdown file that defines a worker with its own context, tools and permissions. Claude delegates to it by description and receives a summary.

SectionsKey conceptsExercisesCommon pitfallsLower priorityQuick referenceReview questionsSources

Key concepts Retain these.

01A subagent works in its own context and returns a summary

Use one when a side task would flood the main conversation with search results, logs or file contents. The subagent does the work separately and returns only the result.1,2
WhyThe main context stays small. Subagent requests still count toward the same usage limits.
  1. “Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions.” — Subagents > Overview
  2. “the subagent does that work in its own context and returns only the summary” — Subagents > Overview

02A subagent is a Markdown file with YAML frontmatter

Only name and description are required. The Markdown body is the system prompt. tools, model, permissionMode, maxTurns, skills, mcpServers, hooks and memory are optional. You can also ask Claude to write the file for you.1,2
WhyA file without a name is treated as documentation, and one without a description is skipped.
  1. “Subagents are Markdown files with YAML frontmatter.” — Subagents > Quickstart
  2. “Only name and description are required.” — Subagents > Frontmatter reference

03The description drives delegation

Claude compares your request with each subagent's description. Include a phrase such as 'use proactively' to encourage delegation. Keep descriptions short; detail belongs in the system prompt.1,2
WhyCombined descriptions over 15,000 tokens trigger a startup warning. Vague descriptions mean unreliable delegation.
  1. “Claude uses each subagent's description to decide when to delegate tasks.” — Subagents > Overview
  2. “To encourage proactive delegation, include phrases like "use proactively" in your subagent's description field.” — Subagents > Automatic delegation

04Scope decides which definition wins

Managed settings override the --agents flag, which overrides project .claude/agents/, which overrides user ~/.claude/agents/, which overrides plugin agents. Commit project subagents so the team shares them.1
WhyA same-named subagent in a higher location silently replaces the lower one.
  1. “When multiple subagents share the same name, Claude Code uses the one from the higher-priority location.” — Subagents > Choose the subagent scope

05Restrict capabilities with tools and permissions

A subagent inherits all tools if tools is omitted. Use tools as an allowlist or disallowedTools as a denylist. permissionMode sets how permission prompts behave.1,2
WhyRestricting tools is the main way to make a reviewer read-only and keep it that way.
  1. “Inherits every tool available to subagents if omitted.” — Subagents > Frontmatter reference
  2. “Tools to deny, removed from inherited or specified list.” — Subagents > Frontmatter reference

06Subagents start in the background by default

A subagent Claude spawns from the main conversation runs concurrently unless you change it. Foreground subagents block the conversation and pass permission prompts to you. Background ones surface prompts in the main session.1,2
WhyDo not assume the result is available in the same turn.
  1. “With nothing configured, a subagent that Claude spawns from your main conversation starts in the background.” — Subagents > Foreground or background
  2. “Foreground subagents block the main conversation until complete.” — Subagents > Foreground or background

07Choose a subagent only when isolation helps

Use the main conversation for back-and-forth, shared context across phases, quick edits and low latency. Use a subagent for verbose output, enforced tool limits, or self-contained work that returns a summary.1,2
WhyA subagent that is not a fork starts fresh and needs time to gather context.
  1. “The task produces verbose output you don't need in your main context” — Subagents > Subagents or main conversation
  2. “The work is self-contained and can return a summary” — Subagents > Subagents or main conversation

Exercises Hands-on practice.

01Create a read-only reviewer

Write a subagent file and see automatic delegation.
  1. Create .claude/agents/code-reviewer.md with the content below
  2. Wait a few seconds; Claude Code watches the directory and no restart is needed
  3. Ask: 'Have the code-reviewer subagent look at my recent changes'
---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. Analyze the code and report issues by priority.
VerifyThe review arrives as a summary and the subagent made no edits.
VariationRemove the tools line and check whether the subagent can now edit files.

02Force a specific subagent

Compare natural-language requests with an @-mention.
  1. Type @ and select code-reviewer (agent) from the typeahead
  2. Add a task, such as 'look at the auth changes'
  3. Repeat with a plain-language request and compare
VerifyThe @-mention always runs that subagent; the plain request leaves the decision to Claude.
VariationRewrite the description with 'use proactively' and observe whether Claude delegates unprompted.

03Break a frontmatter field on purpose

Learn how misspelled fields fail.
  1. In your reviewer file, rename tools to Tools
  2. Start a session with claude --debug
  3. Search ~/.claude/debug/<session-id>.txt for does not recognize or apply
VerifyThe debug log names the unrecognised field, and no error appears in the session.
VariationDelete the description line and confirm the file is skipped.

Common pitfalls

  • Field names are camelCase and must match exactly. An unrecognized field is ignored without an error.
  • A file is skipped silently when it has no description, its YAML does not parse, or its opening --- is not the first line. Check with --debug.
  • A new agents directory created mid-session needs a restart. So do edits under --add-dir directories.
  • The AskUserQuestion and EnterPlanMode tools are removed from every subagent.
  • Spawning fails with Concurrent subagent limit reached at 20 running subagents.

Lower priority Valid but rarely needed. Consult when required.

Worktrees

Source: https://code.claude.com/docs/en/worktrees · Retrieved 2026-11-11 · 4 min read

A git worktree gives each Claude Code session its own files and branch on shared history, so parallel sessions and subagents do not overwrite each other.

SectionsKey conceptsExercisesCommon pitfallsLower priorityQuick referenceReview questionsSources

Key concepts Retain these.

01One session, one worktree

A worktree is a separate working directory and branch that shares the repository history. Each session in its own worktree edits its own copy of the files.1
WhyTwo sessions editing one checkout produce conflicting changes.
  1. “Running each Claude Code session in its own worktree gives it a separate copy of the files to edit” — Worktrees

02Start with --worktree

claude --worktree <name> (or -w) creates .claude/worktrees/<name>/ on a new branch worktree-<name> and starts the session there. You can also ask Claude to 'work in a worktree' mid-session.1,2
WhyA single flag gives full isolation; no manual git commands are needed.
  1. “Pass --worktree or -w with a name to create an isolated worktree and start Claude in it.” — Worktrees > Start Claude in a worktree
  2. “Add .claude/worktrees/ to your .gitignore so worktree contents don't appear as untracked files in your main checkout.” — Worktrees > Start Claude in a worktree

03A worktree is a fresh checkout

Dependencies and gitignored files such as .env are not present. Install dependencies in the worktree, or list files to copy in a .worktreeinclude file.1
WhyBuilds and tests fail in a new worktree until the environment is set up.
  1. “A worktree is a fresh checkout, so initialize your development environment there” — Worktrees > Set up the environment

04Isolation is enforced, with a gap

In a worktree session, Claude Code blocks edits, command working directories and git redirects that target the main checkout. It does not track files a shell command writes, so cp or a redirect into the main checkout is not blocked by these checks.1,2
WhyTreat isolation as protection for normal edits, not a sandbox.
  1. “Claude Code blocks an Edit, Write, or NotebookEdit that targets a path in the main checkout.” — Worktrees > Enforcing isolation
  2. “None of them tracks which files a shell command writes” — Worktrees > Enforcing isolation

05Subagents can each get a worktree

Ask Claude to 'use worktrees for your agents', or add isolation: worktree to a subagent's frontmatter. A subagent worktree with no changes is removed automatically.1,2
WhyParallel subagents that edit files need the same isolation as parallel sessions.
  1. “by adding isolation: worktree to its frontmatter.” — Worktrees > Isolate subagents
  2. “Claude Code removes automatically when the subagent finishes without changes” — Worktrees > Isolate subagents

06Some things are shared with the main checkout

The .git directory, project-scope plugins, 'don't ask again' permission approvals, and untracked skills, agents and commands (when the worktree has none of its own).1
WhyAn approval granted in one worktree applies to every worktree of the repository.
  1. “git commands in a worktree write to the main repository's shared .git directory” — Worktrees > What is shared

Exercises Hands-on practice.

01Run two isolated sessions

See parallel edits on separate branches.
  1. Add .claude/worktrees/ to .gitignore
  2. In terminal 1: claude --worktree feature-a
  3. In terminal 2: claude --worktree feature-b
  4. Ask each session to edit the same file differently
Verifygit worktree list shows both worktrees, and git branch shows worktree-feature-a and worktree-feature-b with separate changes.
VariationOmit the name and note the generated one.

02Make a subagent always isolate

Use isolation: worktree.
  1. Create .claude/agents/refactorer.md with isolation: worktree in the frontmatter
  2. Ask Claude to use the refactorer for a small rename
  3. Run git worktree list while it runs
VerifyA temporary worktree appears and the main checkout is unchanged.
VariationAsk for a change that produces no diff and confirm the worktree is removed.

Common pitfalls

  • Interactive --worktree runs need workspace trust; run claude once in the directory first.
  • ${CLAUDE_PROJECT_DIR} in hooks stays at the original project root after entering a worktree; read cwd from the hook input instead.
  • If permissions.blockWritesOutsideWorkingDirectories is on, Claude has no EnterWorktree tool; start with claude --worktree instead.
  • Worktrees require a git repository.

Lower priority Valid but rarely needed. Consult when required.

Dynamic Workflows

Source: https://code.claude.com/docs/en/workflows · Retrieved 2026-11-11 · 5 min read

A dynamic workflow is a script Claude writes to run many subagents in the background. The script, not Claude, holds the plan and the intermediate results.

SectionsKey conceptsExercisesCommon pitfallsLower priorityQuick referenceReview questionsSources

Key concepts Retain these.

01The script holds the plan

With subagents, skills and agent teams, Claude decides each next step. In a workflow, a JavaScript script does: loops, branching and intermediate results live in script variables, and only the final answer reaches Claude's context.1,2
WhyLarge jobs no longer fill the context window, and the orchestration can be read and rerun.
  1. “The difference is who holds the plan” — Workflows > When to use a workflow
  2. “A workflow script holds the loop, the branching, and the intermediate results itself, so Claude's context holds only the final answer.” — Workflows > When to use a workflow

02Use one for scale or cross-checking

Suited to codebase-wide audits, large migrations, research with sources checked against each other, and plans drafted from several angles. Agents can review each other's findings before reporting.1
WhyFor a few delegated tasks, plain subagents are cheaper and simpler.
  1. “Claude writes the script for the task you describe, and a runtime executes it in the background while your session stays responsive.” — Workflows

03Start one with a keyword or a bundled command

Include ultracode in your prompt, or ask in plain words ('use a workflow'). /deep-research <question> is the bundled example. /effort ultracode makes Claude plan a workflow for every substantive task.1,2
WhyThe keyword only changes how work is structured; permission checks still apply.
  1. “include the keyword ultracode in your prompt” — Workflows > Ask for a workflow
  2. “Run /deep-research with a question you want investigated.” — Workflows > Run a bundled workflow

04Runs are autonomous and bounded

No user input mid-run. Up to 16 concurrent agents by default and 1,000 agents per run. The script has no direct filesystem or shell access; its agents do the work. Watch and stop runs in /workflows.1,2
WhyIf you need sign-off between stages, run each stage as its own workflow.
  1. “No mid-run user input” — Workflows > Behavior and limits

01A plugin is a directory of components with a manifest

  2. “Local scope: enabled for you in this repository only” — Plugins > Install scopes

  2. “The full text of a skill or agent loads only when it's used.” — Plugins > What an enabled plugin adds
