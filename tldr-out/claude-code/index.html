Claude Code skills and plugins

From code.claude.com/docs · condensed 11 November 2026 · 20 min read

These pages condense about 2,800 lines of the Claude Code documentation on skills and plugins, the two main ways to teach Claude Code a procedure and share it, into about 20 minutes of reading. They are written for someone who already uses Claude Code day to day and has never written a skill.

When you finish, you should be able to write a skill that triggers when it should, decide whether a setup needs to be a plugin, and avoid the mistakes that make either one silently do nothing.

BackgroundGeneral knowledge, not from the source documentation.

What to know first

Claude Code works within a context window: everything Claude can see on a turn, including the conversation, files it has read and loaded instructions. Anything that sits in context on every turn costs tokens on every turn.

CLAUDE.md files hold instructions that load at the start of every session. Slash commands are messages that start with /, such as /help. Subagents are separate assistants with their own context window that Claude can hand a task to. Hooks are commands that Claude Code itself runs on events such as a file edit; they do not depend on Claude’s judgment.

How the pieces fit

All four ways of extending Claude Code carry instructions or behavior. They differ in when they load and who decides to use them:

MechanismLoadsWho decides it runsUse it for
CLAUDE.mdEvery session, in fullAlways onShort facts about the project
SkillDescription always; body when invokedClaude (from the description) or you (/name)Procedures, checklists, reference material
HookRegistered at startupFires on its event, every timeRules that must always hold
PluginEvery enabled component, every sessionYou, by installing and enabling itShipping several of the above as one unit

Reading paths

  • Write your first skill (8 minutes): Skills, from the start through “By example”.
  • Share a setup with your team (20 minutes): all of Skills, then Plugins.
  • Install someone else’s plugin safely (5 minutes): in Plugins, read “How it works”, “Recipes” and “Pitfalls”.

This page covers writing and running skills. To package skills with agents, hooks and MCP servers for other people, see Plugins.

A skill is a folder holding a SKILL.md file. The file has two parts: YAML front matter that says when to use the skill, and Markdown instructions that Claude follows when it runs.[6] You can run a skill yourself as /skill-name, or Claude can load it on its own when your request matches its description.

Create one when you keep pasting the same instructions, checklist or procedure into chat. Unlike CLAUDE.md, which is in context all the time, a skill’s body loads only when it is used, so a long procedure costs almost nothing until you need it.[7]

How it works

Main article: Extend Claude with skills

Suppose you have thirty skills installed. On every turn, Claude sees a short listing: each skill’s name and description. That is how it knows what exists. The body of a skill, which may be hundreds of lines, enters the conversation only when the skill is invoked.[8] Everything else about skills follows from this two-stage design: what goes in the description, why bodies can be long, and why too many skills crowd each other out.

The description is therefore the trigger. Claude uses it “to decide when to apply the skill”,[1] so it has to contain the words people actually say when they need it. Put the main use case first: the listing truncates each skill’s description at 1,536 characters,[2] and when you have many skills, Claude Code drops whole descriptions, starting with the skills you invoke least, to stay within a budget of 1% of the context window.[3]

Who can invoke it

By default both you and Claude can invoke any skill. Two front matter fields narrow that, and each has a different effect on what sits in context:

Front matterYou can run itClaude can run itIn context before it runs
(neither field)YesYesThe description
disable-model-invocation: trueYesNoNothing[9]
user-invocable: falseNoYesThe description

Use disable-model-invocation: true for anything with side effects, such as deploying, committing or sending messages. The docs’ reason: “You don’t want Claude deciding to deploy because your code looks ready.”[10] Use user-invocable: false for background knowledge that makes no sense as a command, such as how a legacy system works.

Where you type the name matters too. /deploy staging at the start of a message runs the skill. Typed after other words, as in “go ahead and /deploy to staging”, the name only gives Claude permission to run it.[11]

Once loaded, it stays

When a skill runs, Claude Code renders it and adds the result to the conversation “as a single message”, where it stays across later turns.[12] Claude Code “does not re-read the skill file on later turns”.[13] Two consequences follow:

  • Write standing instructions, not one-time steps. “Run the tests after every edit” keeps working; “Run the tests” is done once and forgotten.
  • Put the important rules first. When the conversation is compacted, Claude Code re-attaches each invoked skill but keeps only its first 5,000 tokens, within 25,000 tokens for all skills together.[4]

Permissions don’t persist the way the text does. An allowed-tools grant clears when you send your next message,[14] and invoking the skill again grants it again.

Before Claude reads it: arguments and live data

Claude Code processes the file before Claude sees it. It substitutes arguments, such as $ARGUMENTS, $0 and $1, and it runs every line of the form !`command`, replacing the line with the command’s output. “Claude receives actual data, not the command itself.”[15]

This preprocessing is all-or-nothing: “A failed command aborts the entire skill invocation, not just its own placeholder.”[16] With the default bash shell, any non-zero exit code counts as a failure, except exit code 1 from search and comparison commands.

Where it lives decides who gets it

The folder a skill sits in decides which sessions load it. Save it under your home directory for every project, commit it to a repository to share it with the team, or ship it in a plugin.

LocationPathLoads in
Personal~/.claude/skills/<name>/SKILL.mdAll your projects on this machine, but not Cowork or cloud sessions[17]
Project.claude/skills/<name>/SKILL.mdSessions in this repository; commit it for your team
Nested<subdir>/.claude/skills/<name>/SKILL.mdOnce Claude works on files in <subdir>
Enterprise.claude/skills/ in the managed settings directoryEvery user your organization deploys it to
Plugin<plugin>/skills/<name>/SKILL.mdWherever the plugin is enabled, as /plugin-name:skill-name

Claude Code also reads .claude/skills/ in every parent directory up to the repository root,[18] so starting in packages/frontend/ still picks up skills defined at the root. Skills in subdirectories below where you started load only the first time Claude reads or edits a file there.[19]

Plugin skills never collide with these: both load, “because plugin skills are namespaced as /plugin-name:skill-name”.[20] A skill with the same name as a bundled skill or a built-in command replaces that command, but not its aliases.

Running in a subagent: context: fork

With context: fork in the front matter, the skill runs in a new subagent of the type named in agent (default general-purpose), with the skill’s content as its task. “The subagent doesn’t see your conversation history, so the skill’s instructions have to stand on their own.”[21] It runs in the background by default and posts its result when done; background: false makes the turn wait for it.

WarningFork only skills that contain a task. A skill made of guidelines alone, such as “use these API conventions”, gives the subagent nothing to do, and it “returns without meaningful output”.[22]

Supporting files

A skill folder can hold more than SKILL.md. Claude reads the extra files only when the instructions point to them, so detailed material costs nothing until needed. Keep SKILL.md itself under 500 lines.[5]

WarningReview allowed-tools in repositories you clone

allowed-tools grants permissions; it does not restrict tools, since every tool “remains callable”.[31] Workspace trust doesn’t gate the field,[32] so a project skill can pre-approve broad commands for itself. Read the skills in a repository before you run Claude Code there.

Check yourself

  1. What does Claude see about a skill before the skill runs, and why does it matter?

    Only its name and description, in the skill listing. The description is the sole basis for Claude choosing the skill, so it must contain the words users actually say.[1]

  2. You want Claude never to deploy on its own initiative. Which field do you set, and what else changes?

    disable-model-invocation: true. The description also leaves Claude’s context, so the skill costs nothing until you run it.[9]

  3. A skill tells Claude to run the tests. Ten turns later Claude has stopped running them. Why?

    The skill was added once as a message and the file is not re-read, so a one-time step stays done. Word it as a standing rule (“after every edit”), or use a hook if it must always happen.[13]

  4. You have deploy in both ~/.claude/skills/ and the project’s .claude/skills/. Which runs for /deploy?

    The personal one: enterprise beats personal, and personal beats project.[33]

  5. Your skill’s !`npm test` fails. What does Claude see?

    Nothing from the skill. A failed command aborts the whole invocation.[16]

  6. When is context: fork the wrong choice?

    When the skill is guidelines rather than a task, or when the task needs the current conversation. The forked subagent sees neither your history nor an actionable prompt.[21]

Not the Claude Code extension for VS Code or the JetBrains plugin for running Claude Code in an IDE.

A Claude Code plugin is “a directory of skills, agents, hooks, MCP servers, or other components that Claude Code installs and loads as one unit.”[1] A small JSON manifest gives it a name, and that name becomes a prefix on everything inside it. Most plugins are installed from a marketplace, a catalog listing plugins and where to fetch them.

You don’t need a plugin to use a skill, a hook or an MCP server; each works on its own.[2] Reach for a plugin when you want several of them “packaged as one unit”:[3] to install a setup someone else built with one command, or to give yours to a team, install it across projects, and ship versioned updates.

How it works

Main article: Plugins overview

A plugin is an ordinary directory. Each kind of component has a fixed folder under the plugin root, and the manifest sits apart from them in .claude-plugin/.

From a marketplace to your session

A marketplace is a repository or folder with a .claude-plugin/marketplace.json file. “It’s a catalog, not a hosted store”:[4] it lists plugins and says where to fetch each one. Claude Code adds Anthropic’s official marketplace the first time you start an interactive terminal session.[5] You add any other marketplace once, then install its plugins by name, as plugin@marketplace.

During development you skip the marketplace entirely: --plugin-dir “loads a directory or .zip archive for one session.”[6]

Enabled means present in every session

“An enabled plugin is part of every session, not only the sessions where you use it.”[7] That has three costs to weigh before installing:

  • Context. The name and description of every skill and agent that Claude can invoke on its own sit in context on every turn, as with standalone skills. Full text loads only when used.
  • Processes. Its MCP servers run alongside each session, and its hooks fire on their events. Hooks don’t wait for one of the plugin’s skills to be used.[8]
  • Permissions. “What the plugin runs, it runs as you.”[9] This holds for every marketplace tier, official ones included.

To stop a plugin without uninstalling it, disable it.

Scopes decide who has it

When you install, you pick a scope, and the scope decides which settings file records the plugin as enabled.

The local setting overrides the project setting, which overrides the user setting.[10] Project scope has a catch: committing the setting “turns the plugin on for your collaborators but doesn’t download it to their machines.”[11] Each collaborator installs it once per clone. Cloud sessions, including claude.ai/code, don’t load plugins from your local settings at all.[12]

Names get a prefix

Inside a plugin, skills and agents take the plugin’s name as a prefix, “so two plugins can each provide a hello skill without colliding.”[13] The manifest’s name is the only required field, because it becomes that prefix.[14]

Updates

Auto-update is on for Anthropic’s official marketplaces and off for every other marketplace, “including the community marketplace, third-party marketplaces, and local development marketplaces.”[21] An update changes the files on disk, but “the running session keeps the versions it already loaded”;[22] run /reload-plugins or start a new session.

Check yourself

  1. You have one skill you want in all your projects. Do you need a plugin?

    No. Save it in ~/.claude/skills/. Plugins are for bundling several components or for sharing and versioning them.[2]

  2. A plugin you installed hasn’t been used all week. Is it costing you anything?

    Yes. An enabled plugin is part of every session: its descriptions take context, its MCP servers run and its hooks fire. Disable it if you don’t need it.[7]

  3. A plugin is enabled at user scope, and .claude/settings.local.json disables it. Is it on in this repository?

    No. Local overrides project, which overrides user.[10]

  4. You committed a plugin at project scope, but a teammate’s session doesn’t have it. Why?

    Project scope enables the plugin but doesn’t download it. The teammate installs it once in their clone.[11]

  5. To keep the plugin root tidy, you move skills/ into .claude-plugin/. What happens?

    The plugin still loads, but its skills don’t. Only plugin.json goes in .claude-plugin/; components go at the plugin root.[26]

  6. Where should a plugin keep a downloaded cache so that it survives updates?

    In ${CLAUDE_PLUGIN_DATA}. ${CLAUDE_PLUGIN_ROOT} changes with every version.[20]
